## 本轮修复记录

### 修复项 D-1：worker 缺失时 run 永久卡在 pending，对话界面「无任何反应」

- **Bug 现象**：前端发送消息后按钮变为「停止回答」，一直不结束，界面没有任何提示；数据库 `agent_runs` 里 run 永久停在 `pending`。
- **根因**：
  1. 运行耗时任务依赖 ARQ worker 消费 Redis 队列，而本地开发启动指南没有列 worker 进程，缺失时 run 入队后无人消费；
  2. 更关键的是代码缺陷：run 卡在 `pending` 时既不报错也不超时，线程被永久占用，前端 SSE 流无限等待，用户侧表现就是「没有任何反应」。
- **修复内容**：
  - `backend/package/yuxi/services/agent_run_service.py`：新增 `_is_stalled_pending_run` / `_fail_stalled_pending_run`，run 停在 `pending` 超过 `RUN_PENDING_TIMEOUT_SECONDS`（默认 60s）即置为 `failed`（`error_type=worker_unavailable`）并回传 error/end 事件；`prepare_agent_run_creation_scope` 在放行新请求前先释放这类僵死 run，避免线程锁死。
  - `web/src/composables/useAgentStreamHandler.js`：error 事件兼容 `error_message` 字段，确保错误文案能展示给用户。
  - `docs/develop-guides/local-dev-environment.md`：补入 worker 启动步骤与「对话无反应」的排查条目。
  - `backend/test/unit/services/test_agent_run_service.py`：补充卡死检测单元测试。
- **修复前实测**：run 长期 `pending`，界面停在「停止回答」，无任何错误提示。
- **修复后实测**：3 次复现均在 +61s 自动 failed（`error_type=worker_unavailable`，文案「后台任务进程未运行，请检查 worker 服务是否已启动」）；前端解除「停止回答」并弹出错误提示；同一线程后续消息可继续发送。
- **补充验证**：worker 启动后，队列中积压的 4 个僵死 run 被 worker 拉取并按「Run already terminal, skip」跳过，无重复执行、无竞态。

### 修复项 D-2：研究助手场景下「新建对话 / 切换智能体」互锁，用户无法换智能体

- **Bug 现象**：默认智能体是「AI 研究助手」。侧边栏点「新对话」没有任何变化（URL、消息列表都不变）；输入区智能体下拉里「智能助手 / 深度研究」被置灰，点击只提示「当前对话已绑定智能体，请新建对话后切换」，而「新对话」又永远清不掉当前绑定，形成死路。
- **根因**：
  1. 研究助手会话按「知识库+项目」作用域绑定，后端 `POST /api/research/copilot/thread` 是幂等 ensure，路由切到无 `thread_id` 时前端会立即重新 ensure 出同一条作用域会话；
  2. 智能体下拉用 `hasActiveThread`（即是否存在当前线程）禁用了其他智能体项，切换被硬阻断；
  3. 线程回填期间 `syncingRouteThread` 为 true，会吞掉 `thread-change` 事件，地址栏可能残留旧 `thread_id`。
- **修复内容**（仅前端 `web/src/views/AgentView.vue`）：
  - 切换智能体时不再拒绝，而是先切智能体、再清空当前线程并同步地址栏（`router.replace({name:'AgentComp'})`）；
  - 切回研究助手时显式调用 `ensureResearchThread()` 重新绑定作用域会话；
  - 下拉项不再置灰，提示文案改为「切换智能体将开启新对话。」。
- **修复前实测**：下拉中其他智能体为 `disabled`，点击仅弹提示；「新对话」后 URL 仍为 `/agent/ebcea969…`、消息列表不变。
- **修复后实测**：
  1. 研究助手 → 智能助手：URL 变为 `/agent`、当前线程清空、输入区显示欢迎语、侧边栏历史清空；发消息后自动创建新会话 `59b69633…` 并正常流式返回；
  2. 智能助手 → 研究助手：自动恢复 `ebcea969…` 作用域会话与历史消息，知识库/项目选择条重新出现；
  3. 刷新后重复上述切换，结果一致。

### 修复项 D-3：沙箱服务不可达，工具返回 `[Errno 11001] getaddrinfo failed`

- **Bug 现象**：在「智能助手」会话中要求执行命令，工具卡片能正常显示，但工具输出恒为 `Error: [Errno 11001] getaddrinfo failed`；模型据此回答「沙箱环境不可用」。
- **根因**：
  1. 后端沙箱客户端在地址解析失败时直接抛出 `httpx.ConnectError`，原始 socket 错误既不区分「服务没启动」也不区分「地址配错」，调用方无法定位；
  2. 本地以原生进程运行后端 / worker 时未设置 `SANDBOX_PROVISIONER_URL`，回落到仅在容器网络内可解析的默认域名 `http://sandbox-provisioner:8002`；
  3. `sandbox-provisioner` 容器根本未启动，本地开发启动指南也没有该服务的条目。
- **修复内容**：
  - `backend/package/yuxi/agents/backends/sandbox/provisioner_client.py`：`_request` 捕获 `httpx.ConnectError`，转换为携带当前地址与排查方向的 `RuntimeError`，不再把裸 DNS 错误码透出给模型。

### 修复项 D-6：本地原生启动未加载根 `.env`，模型密钥缺失导致对话一律失败（B28）

- **Bug 现象**：内嵌 AI 研究助手发送消息后提示「智能体运行失败」；后端日志 `Agent chat stream failed (error_type=ValueError)`、`Did not find openai_api_key`，请求 `https://api.deepseek.com/v1` 直接连接失败。

  - `uv run --no-sync --env-file ../.env arq server.worker_main.WorkerSettings`

## 「对话没反应」是模型问题还是代码问题的结论

**结论：是代码 / 环境问题，不是模型问题。** 依据如下：

1. **模型侧正常**：数据库 `model_providers` 中 `deepseek:deepseek-chat` 为已启用状态；同环境下研究助手已产出带真实引用的完整回答（run `1a9ad44a…`，返回检索运行 ID `d6c611d8…`、6 篇含作者 / DOI / 被引数的论文）。模型可以正常出字，不需要更换渠道。
