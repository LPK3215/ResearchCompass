# 6. 定向产出（竞赛方案参考 + 通用学习）

> 按用户分析目的，本仓库最匹配两种场景：**竞赛方案参考**（倒推参赛方案外壳/交互）+ **通用学习**（若做类似项目第一步抄哪、改哪）。其余场景（面试/论文）如需可补。

---

## 6.A 竞赛方案参考：倒推参赛方案可借鉴点

**该仓库解决何种形态的问题**：
"科研人员面对海量文献，无法快速获得『可溯源、可复现、数据不出域』的结构化洞察（创新点/方法论/研究空白/证据综述/引用脉络）。"

**用了什么外壳 / 交互（可倒推借鉴）**：

1. **对话优先 + 工作台检视双层 UI**
   表层是对话（Copilot 驱动，人不点），底层是工作台（agent 执行流程与证据的检视器）。竞赛 demo 不必堆砌操作页，用"一句话触发→可视化过程"更容易出彩。

2. **证据可核查作为差异化尖刀**
   不堆功能广度，而是把"每段结论绑定可点击证据 + 反幻觉校验标色"做成显眼能力。竞赛评审对"过程可信"敏感度高，这是一个高区分度卖点。

3. **自托管 / 数据不出域**
   本地 Docker Compose 一键起（api/web/postgres/redis/lightrag/arq）。竞赛方案若强调"隐私/合规"，这套私有化部署形态可直接借鉴。

4. **填空式二次开发叙事**
   竞赛答辩可讲述"在成熟框架上做领域填空而非造轮子"的工程智慧，体现架构成熟度（比"从零自研"更有说服力）。

**倒推参赛方案的借鉴清单**：
- [ ] 选一个"通用模型能做但不可信"的切入点（仿"上传PDF→分析"不稀缺，要加可信层）
- [ ] UI 用"对话触发 + 过程可视化"而非表单堆叠
- [ ] 核心差异化 = 可溯源/可复现/不出域 三选一主打
- [ ] 技术叙事强调"复用框架原语 + 精准领域填空"

## 6.B 通用学习：若做类似项目，第一步抄哪、第二步改哪

### 第一步：抄（直接复用本仓库已验证的资产）

1. **抄学术分块解析器**（`academic.py` 的结构化 Chunk 元数据模型）
   → 任何文档型 RAG，先把"章节层级 + 公式标记 + 上下文指针"做进 Chunk，检索质量立刻上一个台阶。

2. **抄领域错误→HTTP 解耦**（`research_copilot_service` + `research_router` 的 exception_handler）
   → 项目一上手就分层，service 可单测，后期不返工。

3. **抄 Run 状态机**（`SearchRun`/`SynthesisRun`/`AnalysisRun` 的生命周期）
   → 长任务从第一天就有"提交→异步跑→状态可见"的骨架，而非临时加轮询。

4. **抄框架接缝模式**（`run_worker` 的 slug + source 白名单）
   → 若在现成 Agent 框架上做领域层，这是最小侵入的扩展范式。

### 第二步：改（按自己场景改造）

1. **改检索融合策略**：本仓库三源（自有库+片段+外部学术库）重排模型硬编码 `ms-marco-MiniLM`。你的场景若是中文/垂直域，换重排模型 + 加领域词典召回。

2. **改综述校验强度**：本仓库 `_verify_synthesis_claims` 是两趟 LLM（生成+校验）。低成本场景可改为单趟带引用约束的 prompt；高合规场景可加人工复核节点。

3. **改图谱后端**：本仓库引用图疑似 Postgres 承载（compose 未见 Neo4j）。规模大时改 Neo4j/图数据库，但保留"双向边 + key 去重 merge"的设计。

4. **补本仓库缺的坑**：**优先补框架↔领域接缝的集成测试**（坑1）。这是本仓库最大的工程负债，你的项目从第一天就加 e2e 冒烟，避免"改动靠心证"的悬空感。

### 学习路径一句话
> 抄它的"分层 + 填空 + 证据可核查"骨架，改它的"重排模型 + 校验强度 + 图后端"，补它的"接缝集成测试"。

## 6.C 若用于面试准备（补充方向，未展开写稿）

可围绕三个高频题准备：
- **"如何保证 RAG 生成内容可信？"** → 答：生成/校验分离 + 句级 source_chunk_ids + 结构化分块溯源（对应模块3、亮点3）
- **"如何在通用框架上做领域扩展而不fork？"** → 答：slug 识别 + source 白名单接缝 + 扩展槽填空（对应 1.1、5.6）
- **"长任务前端如何不阻塞？"** → 答：Run 状态机 + SSE 流式 + 阶段进度（对应 3 模块2/4、5.3）
