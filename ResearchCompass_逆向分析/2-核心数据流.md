# 2. 核心数据流 / 执行链路

> 每条链路均标注真实文件与函数。未读源码的细节标注 ⚠️。

## 链路 1：学术检索（关键词 + 语义混合 + 重排）

**入口**：`research_router.py` → `POST /api/research/search/runs`
**落地**：`research_search_service.py`

```
POST /api/research/search/runs
  └─> ResearchSearchService.run_search(query, project_id, source)
        ├─ 文档检索: doc_retriever.get_relevant_documents(query)
        │     └─ 关键词(BM25) + 语义(向量) 双路召回  ⚠️ 具体 retriever 实现见框架层 doc_retriever
        ├─ 片段检索: chunk_retriever.similarity_search(query, k)
        ├─ 传统学术库(arXiv/SemanticScholar): _search_legacy_papers(...)  ⚠️ 外部 API
        ├─ 重排: FlashrankReranker(model_name="ms-marco-MiniLM-L-12-v2")
        │     .compress_documents(combined, query)
        ├─ 落库: SearchRun 创建 (status=completed / failed)
        └─ 返回 chunks / documents / papers
```

**关键函数**：`run_search`（L137）、`_search_legacy_papers`（L463）、`_cross_encoder_rerank`（L570）、`build_doc_retriever`（L242，组合 semantic+keyword）、`build_chunk_retriever`（L275）。

**设计要点**：纯编排函数，I/O 密集，无领域状态；失败仅记 `SearchRun.status=failed` 不抛框架异常（容错）。

## 链路 2：证据综述（聚类 + LLM 聚合 + 反幻觉校验）

**入口**：`research_router.py` → `POST /api/research/synthesis/runs`
**落地**：`research_synthesis_service.py`

```
POST /api/research/synthesis/runs
  └─> ResearchSynthesisService.run_synthesis(search_run_id, project_id, options)
        ├─ 取检索结果: get_search_run(search_run_id)
        ├─ 聚类: _cluster_chunks(chunks, cluster_by_section)
        │     └─ _cluster_by_embedding (KMeans/HDBSCAN) | _cluster_by_section (按 section_path 分组)
        ├─ LLM 聚合: _stream_synthesize_cluster(...)  ← 流式逐簇生成综述
        ├─ 反幻觉校验: _verify_synthesis_claims(...)
        │     └─ LLM 比对聚类原文，输出每句 claim 的 supported/contradicted/unverified
        ├─ 落库: SynthesisRun (status=completed) + SynthesisCluster + SynthesisClaim
        └─ 流式返回 SynthesisChunk 事件
```

**关键函数**：`run_synthesis`（L127）、`_cluster_chunks`（L635）、`_stream_synthesize_cluster`（L750）、`_verify_synthesis_claims`（L885）、流式事件 `SynthesisChunk`（L112）。

**设计要点**：证据可核查是第一性约束——每段综述句都挂 `source_chunk_ids` + 校验状态，呼应项目"过程须可证明正确"的护城河。

## 链路 3：论文结构化分析（四阶段 LangGraph 工作流）

**入口**：`research_router.py` → `POST /api/research/paper-analysis/runs`
**落地**：`academic_paper_analysis_workflow.py` + `academic_paper_analysis_service.py`

```
POST /api/research/paper-analysis/runs
  └─> AcademicPaperAnalysisService.run_analysis(document_id, stage, ...)
        └─> build_academic_analysis_graph()  ← LangGraph StateGraph
              add_node: structure        → analyze_structure_node
              add_node: innovations      → analyze_innovations_node (调用 LLM 抽创新点)
              add_node: methodology      → analyze_methodology_node
              add_node: gaps             → analyze_gaps_node (研究空白/方向)
              add_edge: START → structure → innovations → methodology → gaps → END
              add_node: analyze_functional_node (可选功能分析)
        执行: graph.ainvoke(initial_state)
        落库: AnalysisRun (status=completed/running/failed) + AnalysisResult
        流式: stream_analysis_progress(...) 回传阶段进度
```

**关键函数**：`build_academic_analysis_graph`（workflow L 未逐行读，已读结构）、`AcademicPaperAnalysisService.run_analysis`（service）、`stream_analysis_progress`（service 流式）。

**设计要点**：固定 DAG 四阶段保证"每篇论文分析路径一致、可复现、可断点续跑"——这是"可证明正确"在论文分析维度的落地。

## 链路 4：引用图谱同步（学术引用关系图谱化）

**入口**：`research_router.py` → `/api/research/graph/*`
**落地**：`academic_graph_service.py`

```
POST /api/research/graph/sync
  └─> AcademicGraphService.sync_document(document_id)
        ├─ 解析引用: extract_citations(document)  ⚠️ 解析实现待读
        ├─ 写图: _upsert_paper_node + _upsert_citation_edge (双向: cited_by / cites)
        ├─ 冲突处理: 节点已存在则 merge（基于 DOI/标题归一化 key）
        └─ 返回 GraphStats (节点数 / 边数 / 连通分量)
```

**关键函数**：`sync_document`、`get_graph_stats`、`_resolve_merge_conflict`（冲突处理命名推断，⚠️ 待逐行确认）。

**设计要点**：引用关系是学术证据链的核心，图谱化后支持"某观点被哪些后续工作引用/反驳"的溯源。

## 链路 5：ResearchCopilot 编排（对话优先的智能体运行）

**入口**：`research_router.py` → `POST /api/research/projects/{id}/chat`
**落地**：`research_copilot_service.py` → `run_worker.py`（框架接缝）

```
POST /api/research/projects/{id}/chat
  └─> ResearchCopilotService.chat(project_id, message, session_id)
        └─ 发框架运行: arq_enqueue(agent_slug=RESEARCH_COPILOT_AGENT_SLUG,
                                    input_metadata={source: RESEARCH_COPILOT_SOURCE,
                                                    research_context: {...}})
              └─ run_worker.py: _trusted_research_context() 校验 source ∈ RESEARCH_CONTEXT_SOURCES
              └─ stream_agent_chat(...)  ← 框架 LangGraph 对话运行时
                    └─ 运行时调用 tools.py 注册的科研工具 (Retrieval/Project/Milestone/Synthesis/Analysis)
        └─ 流式 SSE 返回 agent 回复 + 工具调用轨迹
```

**关键函数**：`ResearchCopilotService.chat`（service）、`run_worker.py` 第 62-70 行 `_trusted_research_context`、第 51 行 `RESEARCH_CONTEXT_SOURCES`。

**设计要点**：Copilot 不是独立实现，而是"框架对话运行时 + 科研工具集"的组合。框架负责调度/上下文/沙盒，领域层只填工具与上下文注入。

## 链路 6：项目治理与报告导出（确定性拼装，不调模型）

**入口**：`research_router.py` → `/api/research/projects/*` + `/api/research/reports/*`
**落地**：`research_project_report_service.py` + `tools.py`（Project/Milestone 工具）

```
POST /api/research/projects  → CreateProject
  └─ tools.py: create_project(...) → ResearchProject 落库

GET /api/research/reports/export  → ResearchProjectReportService.export(project_id, format)
  └─ 确定性拼装: 读 project + milestones + synthesis_runs + analysis_runs
  └─ 渲染: Markdown 模板 | DOCX (python-docx)  ← 不调 LLM，可复现
  └─ 返回文件流
```

**关键函数**：`tools.py` 中 `create_project`/`list_projects`/`update_project`/`create_milestone`；`research_project_report_service.py` 的 `export_report`（⚠️ 函数名未逐行确认，逻辑已读）。

**设计要点**：报告导出走"确定性拼装"路径，刻意绕过 LLM，保证同一项目导出结果稳定、可审计——再次印证"可复现"护城河。
